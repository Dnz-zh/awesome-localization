# Contributing

Know a useful localization tool or spotted something out of date? [Open an issue](https://github.com/ilyaspiridonov/awesome-localization/issues/new) or send a pull request.

## What's a good fit

Recommend a specific software product, application, plugin, or documented API that is available, maintained, and useful for a localization workflow. Explain what it helps someone do and give readers a concrete reason to consider it alongside the products already listed: a different workflow, supported format, integration, deployment option, or audience.

The product is the entry. Use its product name and link directly to its official product page, documentation, or repository. A company that provides language services can develop a qualifying product, but its company website or service offering does not qualify as a tool.

General-purpose software needs a documented localization use. A claim that a product uses AI, offers an API, or supports many languages does not establish which section it belongs in.

## Out of scope

- Translation agencies, language service providers, freelancer profiles, consultants, and vendor directories listed as entries.
- Service packages, quote forms, contact forms, and ordinary service ordering portals presented as software products.
- Waitlists, unavailable products, discontinued tools, and abandoned projects.
- Standalone spreadsheets, document templates, downloadable worksheets, courses, and promotional articles.
- Duplicate listings, affiliate links, referral links, and tracking parameters.
- Unsupported capabilities, invented comparisons, and claims copied from marketing without evidence.

## Suggesting or adding a tool

Include the product's name, direct URL, proposed section, what it helps someone do, and why it adds a useful choice. Link to current official documentation that supports the description and placement. Where the evidence does not establish a fit, defer inclusion until it does. Tell us if you work for the product, own it, receive compensation from it, or have another relevant connection.

For a pull request:

- Add one new product at a time, alphabetically under its main use. List it once, even if it supports several workflows. Distinct products from the same company can qualify separately when their scope and documentation establish the difference.
- Use `- [Name](https://url) - Product description. What you can do with it.` Link to the official product page or repository; put additional evidence links in the PR description.
- Write two short sentences: what it is, then the work it helps someone do. Start the second sentence with an action verb.
- Include a concrete, supported detail such as a workflow, format, integration, review mechanism, or deployment option. Avoid a second sentence that only repeats the section name.
- Use plain language, normal capitalization, and complete sentences ending in periods. Skip slogans, superlatives, price amounts, unsupported quality claims, and promises about turnaround time.
- State important limits when they affect the described use. Do not imply that every language, plan, file format, or deployment supports the same features.

Example:

```markdown
- [Example Review API](https://example.com/docs/review-api) - API for submitting translated text for human proofreading. Send a glossary with each job, request revisions, and retrieve the approved text through callbacks.
```

This example shows the format; every capability in a real submission needs supporting evidence.


### Open-source labels

Use a linked `OSS` label only when the listed product has a verified open-source license. Link to the actual license in the official repository or documentation. A public repository, free tier, or self-hosting option alone is insufficient. Describe source-available products accurately and preserve material restrictions; do not label them OSS. When only a product's core is open source, scope the label and description to that core.

## Changing sections

Propose changes in an issue or pull request. Explain what readers need to find, why the current structure makes that difficult, and which entries would move.

For a new section or a split, show a useful distinction and at least three qualifying products for each resulting section. For a rename or merge, explain how it improves browsing. A new delivery channel, model provider, or AI label alone does not need its own section.

Place tools according to their primary documented workflow. Translation engines produce translations; gateways select or connect engines and models; quality assurance tools detect or assess issues; human review products arrange or support a person's language work. An integration with a tool in another section does not establish the same capabilities.

Update the contents, affected entries, and links to renamed sections together. Taxonomy and maintenance changes can cover multiple entries.

## Editorial independence

Product makers and contributors with vendor connections are welcome to submit eligible products. Disclose your connection; descriptions and placement may be edited for evidence, clarity, and consistency. Payment, backlink exchanges, and requests for stars never determine inclusion or ordering.

## Keeping the list current

Check product links, names, availability, documentation, and important limits before submitting. Include sources with corrections, especially for changes in ownership, licensing, human review, or API access. Update or remove renamed, discontinued, or unsupported entries.

Before opening a PR, check that the product appears once, entries remain alphabetical within each section, the contents links match the headings, and every factual claim has a current source in the PR description.
